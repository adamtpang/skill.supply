## Technical discussion prompts

### Design an alert-triage pipeline for leaked secrets

Start by clarifying scope, users, and error costs. Then propose:

1. Ingest immutable detection events with repository, location, detector,
   timestamp, and redacted metadata. Never place the secret value in logs.
2. Normalize and deduplicate using a stable event or alert key and idempotent
   writes.
3. Enrich with detector confidence, validity status, secret category, repository
   ownership, and provider metadata when available.
4. Rank urgency using validity, blast radius, exposure surface, privilege, age,
   and known ownership. Keep the raw evidence separate from the ranking.
5. Route to the durable owner with an audit trail. Escalate missing ownership as
   a first-class state rather than guessing.
6. Offer safe remediation guidance. Require explicit authorization for
   revocation, history rewriting, or other destructive actions.
7. Measure time to acknowledge, time to owner, time to remediate, false-positive
   rate, duplicate rate, reopened alerts, and missing-owner rate.
8. Design for replay, backfill, redaction, least privilege, rate limits, and
   failure isolation.

State that this is a product and systems hypothesis, not a claim to know GitHub's
private architecture.

### Reduce false positives without increasing missed leaks

- Define a labeled offline dataset with representative repositories, languages,
  detector types, and hard negatives.
- Track precision and recall by segment, not only one aggregate score.
- Include false-negative discovery from incidents, user reports, and shadow
  comparisons.
- Run the candidate path in mirror or darkship mode before changing alerts.
- Compare old and new paths on the same traffic and inspect disagreements.
- Use a private preview to collect workflow feedback, not only model metrics.
- Roll out gradually with guardrails and an immediate rollback path.
- Monitor downstream outcomes such as dismissals, time to triage, and confirmed
  active secrets.

Connect this to the 12-case reconciliation evaluation, but clearly distinguish a
small known-ground-truth harness from GitHub-scale evaluation.

### Ship a detector or validity change safely

Explain the sequence: provider research, least-intrusive validation endpoint,
bounded implementation, unit and integration tests, human review, darkship,
error inspection, documentation-drift correction, staged release, and rollback.
Mention that GitHub publicly describes this workflow. Do not imply Adam has run
it in production.

### Design the API

Discuss explicit state transitions, stable identifiers, idempotency keys,
pagination, authorization, redaction, rate limits, audit events, versioning,
webhook retries, duplicate delivery, and backward-compatible schema evolution.
Ask whether consumers need point-in-time evidence or only the latest alert state.

### Debug an incident

1. Establish severity, user impact, and whether secrets or protected data may be
   exposed.
2. Stop further harm with the smallest reversible mitigation.
3. Preserve evidence and redact sensitive values.
4. Compare recent deploys, flags, dependency changes, provider behavior, and
   traffic shape.
5. Reproduce against a safe fixture or mirror path.
6. Communicate owner, next checkpoint, and uncertainty.
7. Fix, test, stage, and monitor.
8. Document the root cause, detection gap, runbook improvement, and follow-up
   owner after recovery.

State explicitly that Adam has not served a production on-call rotation.
